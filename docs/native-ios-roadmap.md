# Native iOS Feature & Visual Parity Roadmap (Bridge/API contract ready)

This roadmap captures the work required to deliver a fully native SwiftUI implementation of ListIt that stays in lockstep with the shared JavaScript core. Each section bakes in the API/bridge contracts needed so that future code generated by Codex compiles on both macOS and iOS without drift.

## 1. Shared Core & Configuration
- Harden the JavaScript bundle so all web-exposed APIs (listings CRUD, nearby, conversations, uploads, admin tools) are exported under the shared tree (`api.`, `listings.`, `helpers.`, `uploads.`) and callable only through `shared_core_call(method, args)`.
- Eliminate alternate JS entry points (e.g., `api_request`) and preserve the single `shared_core_call` contract.
- Evaluate the bundle through `SharedRuntime`, installing `SharedCoreNativeBridge` before evaluation, and keep the `SharedRuntime` public API stable.
- Use the concrete `SharedCoreClient(runtime:)` from `SharedCoreBridge` for every JS call; do not introduce protocol-based clients or alternate client types.
- Ensure `SharedCoreRequestMeta(silent: Bool = false, priority: String? = nil)` exists with `toDictionary()` and append meta dictionaries to argument arrays only when non-empty.
- Expand Swift service wrappers so each exported API has a native counterpart that:
  - Holds `runtime: SharedRuntime` and `client: SharedCoreClient(runtime: runtime)`.
  - Calls `client.call`, `callObject`, `callString`, `callArray`, or `callDictionary` using the exact method string (e.g., `"api.listMine"`, `"helpers.formatDistance"`) with `[Any]` arguments.
  - Handles optional metadata via `meta?.toDictionary()`.
- Ship the JS bundle via both embedded script and XCFramework options while maintaining the identical `shared_core_call` surface.

## 2. Visual Alignment & Theming
- Capture web palette, typography, spacing, and control shapes in environment theme tokens so `DesignSystemProvider` reproduces consistent styling in SwiftUI and UIKit.
- Provide reusable SwiftUI component variants (brand headers, masonry grids, modal cards, pill filters) that reflect web visuals without bespoke per-screen styling.

## 3. Navigation & Surface Structure
- Mirror browser shell navigation entry points (Listings, Nearby, Messages, Profile, Admin) in a SwiftUI tab/stack hierarchy so primary flows match.
- Surface profile/preferences toggles (auto list, AI description, auto-post nearby, inquiry, notifications) in native settings screens with the same defaults and helper text as the web client.

## 4. Feature Parity Builds
- Nearby: deliver geolocation prompts, radius/search controls, masonry results, and listing actions powered by shared-core via `SharedCoreClient`.
- Listings: add search, filters, infinite scrolling, detail sheets, AI-assisted creation/editing, mass list, and cover management using helpers and upload services from the shared core.
- Messaging: port inbox and thread UI—including unread indicators, attachments, lightbox, and deletion flows—backed by shared messaging APIs.
- Admin: rebuild dashboards, ads management, and reporting workflows using admin endpoints exposed through the shared core.

## 5. Platform Capabilities & Polish
- Connect shared-core events (favorites, uploads, messages, admin alerts) to adapters for haptics, Live Activities, widgets, and intents so native affordances reinforce key interactions.
- Establish SwiftUI previews, snapshot/UI tests, and Fastlane automation that validate themed components and feature flows against shared-core fixtures.

## 6. Build, Targeting, and Tooling Guardrails
- Import `JavaScriptCore` in any file that uses `JSValue`/`JSContext`.
- Ensure `SharedCoreClient.swift`, the `SharedCoreRequestMeta` `toDictionary` extension, `SharedRuntime`, and `SharedCoreNativeBridge` are included in all relevant iOS and macOS targets (or in the `SharedCoreBridge` package target).
- Consolidate duplicate types (e.g., `KeychainStoring`/`KeychainStore`); apply conditional compilation only when necessary and keep one implementation per target.
- Prefer Swift Package Manager for `SharedCoreBridge` and `SharedServices` to avoid Xcode target membership issues and improve reproducibility.
- Lock toolchains by aligning Xcode/Swift versions across machines and documenting the minimum supported versions (or using `tools-version`).
- Add a macOS CI workflow that:
  - Builds and runs tests for all targets on every PR.
  - Loads the JS bundle, invokes `shared_core_call` (e.g., `"helpers.formatDistance"`), and asserts expected results.
  - Instantiates `SharedCoreClient(runtime:)` and exercises `call`/`callObject`/`callString`/`callArray`/`callDictionary` to catch API drift.
- Maintain contract tests that stub `SharedRuntime.call(function: "shared_core_call", with: [method, args])` to guarantee services never depend on alternate entry points or protocols.
- When JS export paths or `shared_core_call` contracts change, update Swift services and tests in the same PR.

## 7. Service Implementation Rules (for Codex & Contributors)
- Always create clients with `SharedCoreClient(runtime: runtime)`—avoid new protocols or alternate clients.
- Use the call helpers to reach JS; never invoke `api_request` or add new JS globals.
- Append `meta.toDictionary()` only when non-empty.
- Keep public API names stable to avoid breaking tests and downstream modules.
- Favor cross-platform APIs already in use (Foundation, JavaScriptCore, SwiftUI/UIKit) and avoid platform-specific calls that would break macOS.

## 8. Shared Runtime Rules (JavaScriptCore)
- Do not use `JSVirtualMachine.performMicrotaskCheckpoint`. It is not available on our Apple platform SDKs.
- When waiting for JS Promises, use a run-loop pump inside `SharedRuntime.resolvePromise`:
  - While waiting on a semaphore, call `RunLoop.current.run(mode: .default, before: Date(timeIntervalSinceNow: 0.001))` to allow microtasks to progress.
- Treat `JSValue.toString()` as optional. Always provide a default when converting to error messages (e.g., `exception.toString() ?? "Unknown JavaScript error"`).
- Keep `SharedRuntime`’s public API stable. Do not change `evaluate(:)`, `call(function:with:)`, or `installNativeBridge(:)` signatures.
- Expose `JSContext` for client use via a read-only `jsContext` computed property; do not mutate the context outside `SharedRuntime` setup and bridge install.

## 9. Bridge/Client Placement & Visibility
- Place `SharedCoreClient` and `SharedCoreRequestMeta` (with `toDictionary()`) in the `SharedCoreBridge` module alongside `SharedRuntime`. Do not duplicate these types in other targets.
- Mark `SharedRuntime` (open), `SharedCoreClient` (public final), and `SharedCoreRequestMeta` (public) so other modules can use them.
- When converting arrays from `JSValue`, use `value.toArray() ?? []` (no redundant downcasts).
- Make utility locators used in public initializers public as needed (e.g., `SharedCoreBundleLocator`) to avoid visibility errors in default argument values.
